Block D: Target ECU (STM32 Bootloader + Application)
--------------------------------------------------------------------------------------------------------

Vai tro: Secure bootloader + Firmware runtime environment.

Noi dung block:

* Hardware Specifications:
  - STM32F103C8T6 (ARM Cortex-M3, 72MHz)
  - 64KB Flash, 20KB RAM
  - Constraint: Memory-efficient design required

* Communication Stack:
  - CAN-TP Server: ISO 15765-2 transport layer
  - UDS Server: ISO 14229-1 diagnostic services
    + 0x10: Diagnostic Session Control
    + 0x22: Read Data By Identifier (firmware version, status)
    + 0x34: Request Download (initiate transfer)
    + 0x36: Transfer Data (receive chunks)
    + 0x37: Request Transfer Exit (trigger verification)
  - NRC 0x78 Keep-Alive Protocol:
    + Response Pending mechanism during time-consuming operations
    + Sent before: ECDSA encrypted (~611ms), AES decrypt (~1562ms), ECDSA plaintext (~611ms)
    + Prevents ESP32 timeout (default 3000ms) during ~5.2s total verification
    + ESP32 retry logic: Max 10 NRC 0x78 messages, resets timeout on each receive

* Security Pipeline: "Verify-then-Decrypt" Architecture (OTA phase only)
  Phase 1 - Verify-then-decrypt:
    1. Verify SHA-256 (Encrypted): Check transport integrity (~21ms)
    2. Send NRC 0x78 (keep-alive) to prevent ESP32 timeout
    3. Verify ECDSA Signature (Encrypted): Authenticate firmware (~611ms)
    4. Send NRC 0x78 before AES decryption
    5. Stream-based AES Decryption: 256-byte chunks (~1562ms) - OTA ONLY!
    6. Verify SHA-256 (Plaintext): Check decryption correctness (~21ms)
    7. Send NRC 0x78 before final ECDSA verification
    8. Verify ECDSA Signature (Plaintext): Secure boot verification (~611ms)
  Phase 2 - Atomic copy:
    9. Erase Slot A (page-by-page)
    10. Copy B->A (256-byte chunks with memcmp read-back verification)
    11. Update BKP->DR2 checkpoint for power-loss recovery (~3s total)
  Phase 3 - Response:
    12. Send UDS 0x77 positive response (only if ALL verifications pass)
    13. Reset MCU to boot into new firmware

NOTE: Secure boot chi co SHA-256 + conditional ECDSA, KHONG co AES!

* Memory Optimization Techniques:
  - Stream-based Decryption: Process 256 bytes at a time
    + No need to buffer entire firmware in RAM
    + RAM usage: <1KB working buffer
  - Chunked Hashing: Process 256-byte blocks sequentially
  - Zero-copy Flash Writes: Decrypt -> Write directly to flash

* Dual-Bank Flash Management:
  - Slot A (Active): Boot from here (0x08007C00)
  - Slot B (Download Buffer): Staging area (0x0800C000)
  - Metadata Pages: FOTA headers (228 bytes each - includes dual signatures)
    + Slot A Metadata: 0x08007800
    + Slot B Metadata: 0x0800BC00

* Secure Boot Logic (every reset):
  - Pre-boot Verification:
    + Read Slot A metadata
    + Compute SHA-256 of application (~21ms)
    + Compare with header hash
    + ALWAYS verify plaintext ECDSA signature (~611ms)
      * Uses header.plaintext_signature field (64 bytes r||s)
      * Guarantees only authorized firmware executes
      * NO conditional logic - secure boot enforced for all firmware
    + NO AES decryption in boot!
  - Vector Table Validation:
    + Check Stack Pointer: 0x20000000-0x20005000 (RAM range)
    + Check Reset Handler: Within application flash range
  - Safe Jump:
    + Disable all interrupts
    + Deinitialize peripherals (CAN, UART, timers)
    + Set SCB->VTOR to app address
    + Load MSP from vector table
    + Jump to Reset Handler

* Power-Loss Recovery:
  - Backup Registers (BKP->DR1, DR2): Persist state across resets
  - State Machine: Track copy progress (page-by-page)
  - Resume Logic: Continue copy from last checkpoint if interrupted

Keywords de showcase:
- "Multi-stage cryptographic verification (OTA phase: SHA-256 -> ECDSA -> AES)"
- "Memory-efficient stream processing (256-byte chunks, AES in OTA only)"
- "Automotive-grade UDS/CAN-TP stack"
- "Power-loss resilient updates"
- "Secure boot with SHA-256 + conditional ECDSA (NO AES in boot!)"
- "Vector table validation for safe execution"

SWIM LANE 1: Python Server (Left column)

Phase: Firmware Preparation

1. Build Application Firmware
- Compile source code (Keil/GCC/IAR)
- Output: Binary file (.bin, ~7284 bytes plaintext)

- Add PKCS7 padding (align to 16-byte blocks)
- Encrypt with pre-shared AES key

4. Calculate Encrypted SHA-256
- Hash encrypted container: sha256
- Purpose: Verify transport integrity

5. ECDSA P-256 Digital Signature
- Sign the encrypted hash with private key
- Output: 64-byte signature (R + S components)

6. Package FOTA Header
- Build 164-byte structure:
  * Magic: "FOTA" (4B)
  * Version: v1.2.1 (3B)
  * Sizes: original_size, encrypted_size (8B)
  * SHA-256 (encrypted): 32B
  * ECDSA signature: 64B
  * AES IV: 16B
  * Original SHA-256: 32B
  * Reserved/padding

7. Upload to Cloud
- Firebase Storage: /firmware/signed/v1.2.1.bin
- Generate public download URL

SWIM LANE 2: ESP32 Gateway (Middle column)
--------------------------------------------------------------------------------------------------------

Phase: Download & Pre-validation

8. Download Firmware
- Cloud Path: HTTPS GET from Firebase
- LAN Path: TCP transfer from Manager
- Buffer in 4KB chunks to SPIFFS/SD card

9. Parse FOTA Header
- Read first 228 bytes (updated from 164 bytes)
- Validate magic == "FOTA"

10. Verify Encrypted SHA-256

--------------------------------------------------------------------------------------------------------
SWIM LANE 3: STM32 ECU (Right column)
--------------------------------------------------------------------------------------------------------

Phase: Verification Pipeline ("Verify-then-Decrypt")

16. Verify Encrypted SHA-256
- Compute SHA-256 (chunked 256-byte processing)
- Time: ~21ms (DWT measured)
- Decision Diamond:
  * NO -> "Erase Slot B & Send Negative Response"
  * YES -> Continue

17. Verify ECDSA Signature
- micro-ecc library (NIST P-256)
- Time: ~611ms
- Decision Diamond:
  * NO -> "Firmware Rejected - Unauthenticated"
  * YES -> Firmware authenticated, safe to decrypt

18. Stream-based AES-128-CBC Decryption
- Loop: Read 256B (encrypted) -> Decrypt -> Write 256B (plaintext)
- IV chaining between chunks
- Time: ~1562ms
- Remove PKCS7 padding bytes
- Result: 7284 bytes plaintext

19. Verify Plaintext SHA-256
- Hash decrypted firmware
- Compare: computed == header.original_sha256
- Decision Diamond:
  * NO -> "Decryption Failed - Erase Slot B"
  * YES -> Integrity confirmed

20. Update Metadata
- Write header to Slot A metadata page (0x08007800)
- Clear AES IV to 0x00 (marker: already decrypted)
- Clear signature (no longer needed)

Phase: Atomic Slot Copy

21. DualSlot_CopyBtoA()
- State machine with backup register persistence
- Process:
  1. Erase Slot A (page-by-page)
  2. Copy B->A (256-byte chunks)
  3. Read-back verify: memcmp() after each write
  4. Update BKP->DR2 (checkpoint progress)
- Power-loss recovery: Resume from last checkpoint
- Time: ~3 seconds

22. Mark Update Complete
- Set BKP->DR1 = 0 (clear force-boot flag)
- Next reset will boot from Slot A

Phase: Secure Boot Check

23. MCU Reset / Power-On
- Enter bootloader main()

24. Check Force-Boot Flag
- Decision: BKP->DR1 == FORCE_BOOT?
  * YES -> Stay in bootloader (wait for UDS commands)
  * NO -> Continue boot sequence

25. Check Copy State
- Decision: BKP->DR2 == COPY_PENDING?
  * YES -> Resume DualSlot_CopyBtoA() from checkpoint
  * NO -> Continue

26. Read Slot A Metadata
- Address: 0x08007800
- Validate: magic == "FOTA"
- Decision: Valid?
  * NO -> "Stay in bootloader - No valid firmware"
  * YES -> Continue

27. Compute Application SHA-256
- Hash application code (0x08007C00)
- Chunked processing (256 bytes)
- Time: ~21ms

28. Compare Hash
- Decision: computed == header.sha256?
  * NO -> "Corrupted firmware - Stay in bootloader"
  * YES -> Continue

29. Check AES IV
- Decision: header.aes_iv != 0x00?
  * YES (Plaintext firmware): Need to verify ECDSA now
    - Run ECDSA verify (~611ms)
    - Decision: Valid? -> YES: Continue | NO: Stay in bootloader
  * NO (Decrypted firmware): Skip ECDSA (already verified during FOTA)

30. Validate Vector Table
- Read SP (0x08007C00)
- Read Reset Handler (0x08007C04)
- Checks:
  * 0x20000000 <= SP <= 0x20005000 (RAM range)
  * Reset Handler in flash range
- Decision: Valid?
  * NO -> "Vector table corrupted - Stay in bootloader"
  * YES -> Continue

31. Jump to Application
- Disable interrupts (clear PRIMASK)
- Deinitialize peripherals (CAN, UART, SysTick)
- Set SCB->VTOR = 0x08007C00
- Load MSP = *(uint32_t*)0x08007C00
- Jump: app_entry = *(uint32_t*)0x08007C04; app_entry();

32. Application Running
- END NODE: "APP START v1.2.1"
- Normal operation mode

SO DO 5: UDS/CAN-TP SEQUENCE DIAGRAM (TOM TAT)

Muc dich: Demonstrate protocol layering, segmentation/reassembly, and flow control for FOTA

Layout: Time-sequence diagram, 3 horizontal lanes (ESP32 Gateway | CAN Bus | STM32 ECU)

========================================================================================================
PROTOCOL STACK IMPLEMENTATION (ISO Standards):
========================================================================================================

APPLICATION LAYER: UDS (ISO 14229-1)
- Services: 0x10 (Session Control), 0x34 (Request Download), 0x36 (Transfer Data), 0x37 (Transfer Exit)
- Message format: [SID | Sub-function/Parameters...]
- Response: Positive [SID+0x40 | Data] or Negative [0x7F | SID | NRC]
- Use case: Diagnostic commands for firmware flashing

TRANSPORT LAYER: CAN-TP (ISO 15765-2)
- Function: Segment large UDS messages (>7 bytes) into CAN frames
- Frame types: SF (Single, ≤7B), FF (First, start transfer), CF (Consecutive, 7B payload), FC (Flow Control)
- Flow control: Block Size (BS) + Separation Time (STmin) manage receiver buffer
- Reassembly: Sequence Number (SN) tracking, timeout detection, error recovery

DATA LINK LAYER: CAN 2.0B
- Frame: 11-bit ID + 8 bytes data
- Bitrate: 125 kbps (automotive standard)
- Hardware: MCP2515 (ESP32 SPI), bxCAN peripheral (STM32 native)

========================================================================================================
PACKET SEQUENCE (Real FOTA Transfer Example):
========================================================================================================

PHASE 1: UDS Session Establishment (Single Frame)
--------------------------------------------------
ESP32 -> STM32: [02 10 02 ...] SF, UDS 0x10 (Programming Session)
STM32 -> ESP32: [06 50 02 00 01 F4 ...] SF, Positive response 0x50
Time: ~5ms

PHASE 2: UDS Request Download (Multi-Frame)
--------------------------------------------
ESP32 -> STM32: [10 0A 34 00 44 08 ...] FF, UDS 0x34, length=10B (address + size)
STM32 -> ESP32: [30 00 00 ...] FC, CTS unlimited, proceed
ESP32 -> STM32: [21 00 C0 00 00 1C 74] CF#1, complete UDS message
STM32 -> ESP32: [04 74 20 10 00 ...] SF, Approved, max block=4096B
Time: ~20ms

PHASE 3: UDS Transfer Data (Heavy Multi-Frame, Critical Section)
-----------------------------------------------------------------
ESP32 -> STM32: [14 02 36 01 <1024B FW>] FF, UDS 0x36, Block#1, length=1026B
                |  |  |  |
                |  |  |  blockSequenceCounter=1
                |  |  UDS SID 0x36
                |  Length=0x0402 (1026 decimal)
                Type: FF (0x10 | high_nibble)

STM32 -> ESP32: [30 08 0A ...] FC, CTS, BS=8 frames, STmin=10ms
                |  |  |
                |  |  Separation Time = 10ms between CF frames
                |  Block Size = Send 8 CF, then wait next FC
                Flow Status = Continue To Send

ESP32 -> STM32: [21 FF 00 00 01 ...] CF#1, SN=1, 7 bytes payload
                -> delay 10ms (esp_rom_delay_us) ->
                [22 02 03 04 05 ...] CF#2, SN=2, 7 bytes
                -> delay 10ms ->
                ... (repeat) ...
                [28 ...] CF#8, SN=8, block complete

ESP32: WAIT for next FC (timeout 1000ms, abort if no response)

STM32 -> ESP32: [30 08 0A ...] FC again, continue pattern

Repeat: ~18 FC-CF cycles for 1026B (146 CF frames total)

STM32 -> ESP32: [02 76 01 ...] SF, UDS 0x76 positive, block acknowledged

ESP32: Repeat PHASE 3 for Block #2-8 (8 blocks × 1024B ≈ 7KB)
Time: ~16 seconds (1.8s per block × 8 + processing overhead)

PHASE 4: UDS Transfer Exit (Verification Trigger)
--------------------------------------------------
ESP32 -> STM32: [01 37 ...] SF, UDS 0x37 (Request Transfer Exit)
STM32: Processing (SHA-256 + ECDSA + AES decrypt + SHA-256 + ECDSA ≈ 5.2s)
STM32 -> ESP32: [03 7F 37 78 ...] NRC 0x78 (Response Pending) before ECDSA #1 (~611ms)
STM32 -> ESP32: [03 7F 37 78 ...] NRC 0x78 before AES decrypt (~1562ms, conditional)
STM32 -> ESP32: [03 7F 37 78 ...] NRC 0x78 before ECDSA #2 (~611ms)
STM32 -> ESP32: [01 77 ...] SF, UDS 0x77 positive, firmware activated
Time: ~5.2 seconds (3x NRC 0x78 prevent ESP32 timeout)

========================================================================================================
KEY TECHNICAL HIGHLIGHTS (Interview-Ready Points):
========================================================================================================

1. PROTOCOL LAYERING:
   - UDS abstracts diagnostic operations, CAN-TP handles transport complexity
   - Separation of concerns: Application logic vs segmentation/flow control
   - Standard compliance: ISO 14229-1 + ISO 15765-2 (universal in automotive)

2. FLOW CONTROL MECHANISM:
   - Purpose: Prevent buffer overflow on receiver (STM32 50KB app, limited RAM)
   - Block Size (BS=8): Tuned to STM32 processing capacity (flash write + verification)
   - STmin (10ms): Balance throughput vs timing precision (esp_rom_delay_us ±50μs accuracy)
   - Adaptive: FC can send WAIT (0x31) if busy, OVFLW (0x32) if abort

3. TIMING & PERFORMANCE:
   - Throughput: 7B payload / 12ms (2ms TX + 10ms STmin) = 583 bytes/sec
   - Optimization potential: STmin=1ms → 5.8s for 7KB (6× faster, requires testing)
   - Timeout strategy: 1000ms for FC/CF, 10000ms for 0x37 (long verification)

4. ERROR HANDLING & ROBUSTNESS:
   - Sequence Number (SN) wrap-around: 0x00-0x0F, detect packet loss/reorder
   - Timeout detection: Abort incomplete transfer, clear buffer
   - Negative Response Codes (NRC): 0x22 (Conditions Not Correct), 0x72 (Programming Failure)
   - Recovery: Retry logic (max 3 attempts), state machine reset

5. REAL-WORLD CONSTRAINTS:
   - CAN bus arbitration: Multi-ECU environment, 125 kbps shared bandwidth
   - Microsecond precision: Automotive timing requirements (AUTOSAR compliance)
   - Flash memory: Write-cycle limits (10K cycles), atomic operations (power-loss safe)

========================================================================================================
PERFORMANCE METRICS (End-to-End FOTA):
========================================================================================================

Total transfer time: ~22 seconds for 7KB firmware
  - UDS 0x10 (Session):           5ms
  - UDS 0x34 (Request):           20ms
  - UDS 0x36 (8 blocks):          16s (dominant factor)
  - UDS 0x37 (Verification):      5.2s (SHA-256 + ECDSA + AES + Copy)
  - Protocol overhead:            ~1s (FC waiting, gaps)

Bottleneck: CAN-TP STmin (10ms) dominates, NOT CAN bitrate (125kbps sufficient)
Optimization: Reduce STmin to 1ms (requires STM32 interrupt priority tuning)

--------------------------------------------------------------------------------------------------------
2.1. BA LOAI FRAME CAN-TP
--------------------------------------------------------------------------------------------------------

FRAME 1: SINGLE FRAME (SF) - Du lieu nho <= 7 bytes
-------------------------------------------------
Structure:
  Byte 0: [0x0N]         N = data length (1-7)
  Byte 1-7: [data...]    Actual payload

Vi du: Gui string "HELLO" (5 bytes)

             |  |  |  |  |  |  |  |
             |  H  E  L  L  O  padding
             Length=5

Use case: UDS requests nho (0x10 01, 0x22 F1 86)

FRAME 2: FIRST FRAME (FF) - Bat dau transfer lon > 7 bytes
---------------------------------------------------------
Structure:
  Byte 0: [0x1X]              X = (total_length >> 8) & 0x0F (4 bits cao)
  Byte 1: [0xYY]              YY = total_length & 0xFF (8 bits thap)
  Byte 2-7: [first 6 bytes]   Dau tien cua payload

Vi du: Transfer 1024 bytes firmware
  Total length = 1024 = 0x0400
  CAN Frame: [10 04 00 36 FF FF ... ]
             |  |  |  |  |  |
             |  |  |  UDS SID 0x36 (Transfer Data)
             |  length_high=4, length_low=0
             Type=FF (0x1X)

Sau FF, sender PHAI doi FC tu receiver!

FRAME 3: CONSECUTIVE FRAME (CF) - Tiep tuc gui data
----------------------------------------------------
Structure:
  Byte 0: [0x2X]         X = Sequence Number (0-F, wrap tu 0 sau 15)
  Byte 1-7: [data...]    7 bytes payload

Vi du: CF sequence
  CF1: [21 AA BB CC DD EE FF 00]  SN=1
  CF2: [22 11 22 33 44 55 66 77]  SN=2
  CF3: [23 88 99 AA BB CC DD EE]  SN=3
  ...
  CF15: [2F ...]                  SN=15
  CF16: [20 ...]                  SN wrap to 0!

Sender phai doi STmin milliseconds giua cac CF.

FRAME 4: FLOW CONTROL (FC) - Receiver control flow
---------------------------------------------------
Structure:
  Byte 0: [0x3X]         X = Flow Status
                         0 = CTS (Continue To Send)
                         1 = WAIT (Buffer full, retry)
                         2 = OVFLW (Overflow, abort)
  Byte 1: [BS]           Block Size (0-255 frames)
                         0 = unlimited, no FC needed until done
                         N = send N frames, then wait next FC
  Byte 2: [STmin]        Separation Time Minimum
                         0x00-0x7F: 0-127 milliseconds
                         0xF1-0xF9: 100-900 microseconds

Vi du: FC response
  [30 08 0A 00 00 00 00 00]
   |  |  |
   |  |  STmin=10ms (0x0A = 10 decimal)
   |  Block Size=8 frames
   FS=CTS (0x30)

Y nghia: "Gui tiep 8 frames, doi 10ms giua moi frame, sau do doi FC tiep theo"

--------------------------------------------------------------------------------------------------------
2.2. FLOW CONTROL MECHANISM - CORE CUA CAN-TP
--------------------------------------------------------------------------------------------------------

VI DU THUC TE: Transfer 7KB firmware

STEP 1: ESP32 gui FIRST FRAME
------------------------------
ESP32 -> CAN Bus:
  [10 1C 74 34 FF 00 00 00]  FF: length=0x1C74 (7284 bytes), data starts
   |  |  |  |
   |  |  |  UDS SID 0x34 (Request Download)
   |  |  length_low=0x74
   |  length_high=0x1C (shifted to 4-bit: 0x1)
   Type=FF

ESP32 STATE: Wait for FC (timeout 1000ms, neu khong co -> abort)

STEP 2: STM32 phan tich va gui FLOW CONTROL
--------------------------------------------
STM32 receives FF:
  - Parse: total_length = (0x01 << 8) | 0xC74 = ... (tinh lai)
  - Actually: Byte0=0x10, extract high nibble=1, Byte1=0xC7, Byte2=0x74
    Wait, format la [0x1X XX ...] voi X contribution
    
Let me recalculate: 0x1C74
  In FF: Byte0=[10+high4bit], Byte1=[low8bit]
  For 0x1C74 = 7284 decimal:
    Byte0 = 0x10 | ((7284 >> 8) & 0x0F) = 0x10 | 0x0C = 0x1C
    Byte1 = 7284 & 0xFF = 0x74
  So frame: [1C 74 34 ...]

STM32 checks:
  - Buffer available? YES (50KB flash buffer in Slot B)
  - Processing capacity? OK (can handle 700 bytes/sec)
  
STM32 -> CAN Bus (FC response):
  [30 08 0A 00 00 00 00 00]
   |  |  |
   |  |  STmin=10ms (gap between CFs)
   |  BS=8 (sau 8 CF thi doi FC tiep)
   FS=CTS (Continue To Send)

STEP 3: ESP32 gui CONSECUTIVE FRAMES (Block 1 - 8 frames)
----------------------------------------------------------
ESP32 STATE: Received FC, extract BS=8, STmin=10ms

ESP32 -> CAN Bus (CF1):
  [21 FF 00 00 01 02 03 04]  SN=1, 7 bytes data
   |
   SN=1 (0x20 | 0x01)

ESP32: delay 10ms (STmin) -> esp_rom_delay_us(10000)

ESP32 -> CAN Bus (CF2):
  [22 05 06 07 08 09 0A 0B]  SN=2

ESP32: delay 10ms

... (repeat 6 more times)

ESP32 -> CAN Bus (CF8):
  [28 1C 1D 1E 1F 20 21 22]  SN=8

ESP32 STATE: Block Size reached (8 frames sent), WAIT for next FC

TIMING ANALYSIS:
  - CF1 transmission: ~2ms (8 bytes @ 125kbps)
  - STmin delay: 10ms
  - CF2 transmission: ~2ms
  - STmin delay: 10ms
  ...
  - Total per block: 8 * (2ms + 10ms) = 96ms
  - Payload per block: 8 * 7 = 56 bytes
  - Effective throughput: 56 / 96ms ≈ 583 bytes/sec (lower than ideal 700 due to CAN overhead)

STEP 4: STM32 gui FC tiep theo
-------------------------------
STM32 receives 8 CF frames:
  - Store to buffer: 56 bytes accumulated
  - Check: More data needed? YES (7284 - 6 - 56 = 7222 bytes remaining)
  - Buffer still OK? YES

STM32 -> CAN Bus:
  [30 08 0A 00 00 00 00 00]  Same FC, continue pattern

STEP 5: Repeat until completion
--------------------------------
Total blocks needed: 7284 bytes / 56 bytes/block ≈ 130 blocks
Total time: 130 * 96ms ≈ 12.5 seconds

Last block handling:
  - Remaining data < 56 bytes? YES
  - ESP32 sends partial CF sequence (e.g., only 3 frames)
  - STM32 detects: Total received == FF length? YES -> Done

--------------------------------------------------------------------------------------------------------
2.3. ERROR HANDLING VA TIMEOUT
--------------------------------------------------------------------------------------------------------

TIMEOUT SCENARIOS:

1. ESP32 waits FC timeout (sau FF hoac sau Block Size)
   - Timeout: 1000ms
   - Action: Abort transfer, send UDS Negative Response

2. STM32 waits CF timeout (sau gui FC)
   - Timeout: 1000ms per frame
   - Action: Abort, erase partial data

3. Sequence Number mismatch
   - Expected: CF SN=5
   - Received: CF SN=7 (packet loss!)
   - Action: Abort, send Negative Response

FLOW CONTROL STATUS CODES:

FC with FS=WAIT (0x31):
  STM32 -> ESP32: [31 00 00 ...]  "Buffer full, retry after delay"
  ESP32: Wait 100ms, resend last FC request
  Use case: STM32 busy processing (e.g., flash write in progress)

FC with FS=OVFLW (0x32):
  STM32 -> ESP32: [32 00 00 ...]  "Buffer overflow, abort!"
  ESP32: Stop immediately, report error to user
  Use case: Firmware size > available buffer (16KB limit exceeded)

--------------------------------------------------------------------------------------------------------
3.1. UDS MESSAGE FORMAT
--------------------------------------------------------------------------------------------------------

REQUEST MESSAGE (ESP32 -> STM32):
  [SID | Sub-function | Parameters...]
   |     |             |
   |     |             Optional, depends on SID
   |     0x01, 0x02... (sub-function)

RESPONSE MESSAGE (STM32 -> ESP32):

            Example: Request 0x22 -> Response 0x62

            |      |      Negative Response Code

            Fixed: 0x7F

--------------------------------------------------------------------------------------------------------
3.2. UDS SERVICES SU DUNG TRONG PROJECT
--------------------------------------------------------------------------------------------------------

SERVICE 0x10: DIAGNOSTIC SESSION CONTROL
========================================
Muc dich: Chuyen session mode (Default -> Programming)

REQUEST (ESP32 -> STM32):
  SF: [02 10 02 00 00 00 00 00]
       |  |  |
       |  |  Sub-function: 0x02 = Programming Session
       |  SID 0x10
       Length=2 bytes

CAN-TP: Single Frame (data <= 7 bytes), khong can FF/CF/FC

RESPONSE (STM32 -> ESP32):
  POSITIVE:
    SF: [06 50 02 00 01 F4 00 00]
         |  |  |  |  |  |
         |  |  |  |  |  Session timeout (500ms = 0x01F4)
         |  |  |  Session parameters
         |  |  Echo sub-function
         |  Response: 0x10+0x40=0x50
         Length=6 bytes
  
  NEGATIVE:
    SF: [03 7F 10 22 00 00 00 00]
         |  |  |  |
         |  |  |  NRC=0x22 (Conditions Not Correct)
         |  |  Original SID=0x10
         |  Negative Response
         Length=3

MEANING: Sau khi vao Programming Session, STM32 cho phep:
  - Flash operations (erase/write)
  - Download firmware
  - Security-sensitive commands

SERVICE 0x22: READ DATA BY IDENTIFIER
======================================
Muc dich: Doc thong tin tu ECU (version, status, etc.)

REQUEST (ESP32 -> STM32):
  SF: [03 22 F1 86 00 00 00 00]
       |  |  |  |
       |  |  |  DID=0xF186 (Active Diagnostic Session)
       |  |  DID high byte
       |  SID 0x22
       Length=3

RESPONSE (STM32 -> ESP32):
  POSITIVE:
    SF: [05 62 F1 86 02 00 00 00]
         |  |  |  |  |
         |  |  |  |  Value=0x02 (Programming Session active)
         |  |  |  Echo DID low
         |  |  Echo DID high
         |  Response 0x62
         Length=5

Use case:
  - DID 0xF186: Current session
  - DID 0xF187: Firmware version (e.g., "v1.2.1")
  - DID 0xF191: ECU serial number

SERVICE 0x34: REQUEST DOWNLOAD
===============================
Muc dich: Thong bao STM32 chuan bi nhan firmware, xin cap phat buffer.

REQUEST (ESP32 -> STM32):
  Format: [SID | dataFormatIdentifier | addressAndLengthFormatIdentifier | memoryAddress | memorySize]

  FF+CF: (vi data > 7 bytes)
    FF: [10 0B 34 00 44 08 00 C0 00]  Length=11 bytes (0x0B)
         |  |  |  |  |  memory_address (little endian)
         |  |  |  addressLengthFormat: 0x44
         |  |  |     High nibble=4 (4 bytes address)
         |  |  |     Low nibble=4 (4 bytes size)
         |  |  dataFormat: 0x00 (uncompressed)
         |  SID 0x34
         Type=FF
    
    FC: [30 00 00 ...]  STM32 response: CTS, unlimited
    
    CF1: [21 00 1C 74 00 00 00 00]  memorySize=0x1C74 (7284 bytes)
          |  memory_size (little endian)
          SN=1

Chi tiet parameters:
  - memoryAddress: 0x0800C000 (Slot B base address)
  - memorySize: 0x00001C74 (7284 bytes firmware)
  - addressLengthFormat: 0x44
    + High nibble 4 = 4 bytes for address field
    + Low nibble 4 = 4 bytes for size field

RESPONSE (STM32 -> ESP32):
  POSITIVE:
    SF: [04 74 20 10 00 00 00 00]
         |  |  |  |
         |  |  |  maxNumberOfBlockLength high (0x1000 = 4096 bytes max per 0x36)
         |  |  lengthFormatIdentifier: 0x20 (2 bytes for block length)
         |  Response 0x74 (0x34+0x40)
         Length=4
  
  NEGATIVE (vi du: not in Programming Session):
    SF: [03 7F 34 22 00 00 00 00]
         |  |  |  NRC=0x22 (Conditions Not Correct)
         |  |  SID 0x34
         |  Negative

MEANING: STM32 confirms:
  - Buffer allocated: 16KB at 0x0800C000 (Slot B)
  - Max block size: 4096 bytes per UDS 0x36 transfer
  - Ready to receive data via 0x36

SERVICE 0x36: TRANSFER DATA
===========================
Muc dich: Gui firmware data theo blocks, lap lai cho den khi xong.

REQUEST (ESP32 -> STM32):
  Format: [SID | blockSequenceCounter | transferRequestParameterRecord (data)]

  Example Block 1 (1024 bytes):
    FF: [1C 04 36 01 FF FF FF FF FF FF]
         |  |  |  |  |_________________|
         |  |  |  |  First 6 bytes of 1024-byte block
         |  |  |  blockSequenceCounter=0x01 (start from 1, wrap at 0xFF->0x00)
         |  |  SID 0x36
         |  Length high
         Type FF (0x1C = 0x10 | 0x0C)
    
    Byte1: 0x04 (length calculation...)
    
    Wait, let me recalculate for 1024 data + 2 header:
    Total UDS message: 1 (SID) + 1 (blockCounter) + 1024 (data) = 1026 bytes
    
    FF: Total=1026 -> [10 04 02 36 01 <first6bytes>]
        Actually: 0x0402 = 1026 decimal ✓
        Byte0: 0x10 | ((1026>>8) & 0x0F) = 0x10 | 0x04 = 0x14
        Byte1: 1026 & 0xFF = 0x02
        So: [14 02 36 01 FF FF ...]
    
    FC: [30 08 0A ...]  STM32: BS=8, STmin=10ms
    
    CF sequence: 1026 - 6 (FF payload) = 1020 bytes remaining
                 1020 / 7 = 145.7 -> 146 CFs needed
    CF1: [21 ...] SN=1
    CF2: [22 ...] SN=2
    ...
    CF146: [2X ...] SN wraps multiple times

RESPONSE (STM32 -> ESP32):
  POSITIVE:
    SF: [02 76 01 00 00 00 00 00]
         |  |  |
         |  |  Echo blockSequenceCounter=0x01
         |  Response 0x76 (0x36+0x40)
         Length=2
  
  After each 0x36, ESP32 waits for 0x76 response, then sends next block.

  NEGATIVE (vi du: hash verification failed):
    SF: [03 7F 36 72 00 00 00 00]
         |  |  |  NRC=0x72 (General Programming Failure)
         |  |  SID 0x36
         |  Negative

LOOP MECHANISM:
  Block 1: ESP32 sends 0x36 (1024 bytes) -> STM32 responds 0x76
  Block 2: ESP32 sends 0x36 (1024 bytes) -> STM32 responds 0x76
  ...
  Block 8: ESP32 sends 0x36 (116 bytes, last block) -> STM32 responds 0x76
  
  Total: 7284 bytes firmware = 7 full blocks (1024*7=7168) + 1 partial (116 bytes)
  NOTE: 7284 bytes is the plaintext firmware size. The encrypted firmware + header (228 bytes) will be larger.

SERVICE 0x37: REQUEST TRANSFER EXIT
====================================
Muc dich: Thong bao transfer hoan thanh, trigger verification.

REQUEST (ESP32 -> STM32):
  SF: [01 37 00 00 00 00 00 00]
       |  |
       |  SID 0x37
       Length=1 (no parameters)

RESPONSE (STM32 -> ESP32):
  POSITIVE (after verification succeeds):
    SF: [01 77 00 00 00 00 00 00]
         |  |
         |  Response 0x77 (0x37+0x40)
         Length=1
  
  NEGATIVE (vi du: SHA-256 mismatch):
    SF: [03 7F 37 72 00 00 00 00]
         |  |  |  NRC=0x72 (General Programming Failure)
         |  |  SID 0x37
         |  Negative

CRITICAL: Sau 0x37, STM32 thuc hien:
  1. Verify SHA-256 (encrypted) - 21ms
  2. Verify ECDSA signature - 611ms
  3. AES decrypt to Slot B - 1562ms
  4. Verify SHA-256 (plaintext) - 21ms
  5. Copy Slot B -> Slot A - 3s
  
  Total: ~5.2 seconds processing time!
  
  ESP32 MUST wait with long timeout (10s recommended).

--------------------------------------------------------------------------------------------------------
3.3. UDS NEGATIVE RESPONSE CODES (NRC) THUONG GAP
--------------------------------------------------------------------------------------------------------

0x11: Service Not Supported
      Cause: SID khong hop le (e.g., 0x99)
      
0x12: Sub-Function Not Supported
      Cause: Sub-function khong ton tai (e.g., 0x10 0xFF)
      
0x13: Incorrect Message Length Or Invalid Format
      Cause: Parameter count sai, missing data
      
0x22: Conditions Not Correct
      Cause: Not in Programming Session, security locked
      Example: Send 0x34 nhung chua gui 0x10 02
      
0x31: Request Out Of Range
      Cause: memoryAddress hoac size vuot qua gioi han
      Example: Request download to 0x08020000 (ngoai 64KB flash)
      
0x33: Security Access Denied
      Cause: Security level chua unlock (if implemented)
      
0x72: General Programming Failure
      Cause: Flash write error, verification failed
      
0x78: Response Pending
      Cause: STM32 busy with time-consuming operation (ECDSA ~611ms, AES ~1562ms)
      Implementation: Sent BEFORE each long operation to prevent client timeout
      Example: During 0x37 processing (5.2s), STM32 sends 3x NRC 0x78 (before ECDSA encrypted, before AES decrypt, before ECDSA plaintext)
      ESP32: Retries up to 10 times, resets 3s timeout on each NRC 0x78

PHAN 4: TICH HOP CAN-TP + UDS - VI DU THUC TE: FOTA FLOW
========================================================================================================

SCENARIO: ESP32 transfer 7KB firmware to STM32

========================================================================================================
STEP 1: UDS 0x10 - Start Programming Session
========================================================================================================

ESP32 (CAN-TP layer):
  Build UDS request: [10 02]  SID=0x10, sub=0x02
  Check length: 2 bytes <= 7 -> Use Single Frame
  Build SF: [02 10 02 00 00 00 00 00]
  Send via CAN: ID=0x7DF (broadcast) or 0x7E0 (STM32 specific)

CAN Bus: ~~~~[02 10 02 ...]~~~> 

STM32 (CAN-TP layer):
  Receive CAN frame
  Parse: Type=SF (0x0X)
  Extract length=2, data=[10 02]
  Pass to UDS layer

STM32 (UDS layer):
  Parse SID=0x10, sub=0x02
  Action: Switch to Programming Session
  Security: Disable bootloader timeout, enable flash commands
  Build response: [50 02 00 01 F4]
  Pass to CAN-TP

STM32 (CAN-TP layer):
  Length=5 <= 7 -> Use SF
  Build: [05 50 02 00 01 F4 00 00]
  Send via CAN: ID=0x7E8 (response ID)

CAN Bus: <~~~[05 50 02 ...]~~~~ 

ESP32 (CAN-TP + UDS):
  Receive SF, parse response 0x50
  Result: Programming Session active ✓

TIME: ~5ms (2ms request + 1ms processing + 2ms response)

========================================================================================================
STEP 2: UDS 0x34 - Request Download
========================================================================================================

ESP32 (UDS layer):
  Build request: [34 00 44 08 00 C0 00 00 1C 74]
                  |  |  |  |_____________| |______|
                  |  |  |  address         size
                  |  |  addressLengthFormat
                  |  dataFormat
                  SID
  Total length: 10 bytes

ESP32 (CAN-TP layer):
  Length=10 > 7 -> Use Multi-Frame (FF + CF)
  Build FF: [10 0A 34 00 44 08]  Length=10 (0x0A), first 4 bytes
            |  |
            Type=FF, length_high=0
  STATE: Wait for FC

CAN Bus: ~~~~[10 0A 34 ...]~~~>

STM32 (CAN-TP layer):
  Receive FF, parse length=10 bytes
  Check buffer: OK (plenty of RAM)
  Build FC: [30 00 00 ...]  CTS, BS=unlimited (0), STmin=0
  Send FC

CAN Bus: <~~~[30 00 00 ...]~~~~

ESP32 (CAN-TP layer):
  Receive FC: FS=CTS, BS=0, STmin=0
  Build CF1: [21 00 C0 00 00 1C 74]  Remaining 6 bytes
             |  |_________________|
             SN=1, last 6 bytes of UDS message
  Send CF1

CAN Bus: ~~~~[21 00 C0 ...]~~~>

STM32 (CAN-TP layer):
  Receive CF1, reassemble: [34 00 44 08 00 C0 00 00 1C 74]
  Complete message received, pass to UDS

STM32 (UDS layer):
  Parse: SID=0x34, address=0x0800C000, size=0x1C74
  Check:
    - Session=Programming? YES ✓
    - Address valid? 0x0800C000 in Slot B range ✓
    - Size fits? 7284 < 16384 (16KB) ✓
  Action: Allocate buffer, prepare flash region
  Build response: [74 20 10 00]  maxBlockLength=0x1000 (4096)
  Pass to CAN-TP

STM32 (CAN-TP layer):
  Length=4 <= 7 -> SF
  Build: [04 74 20 10 00 00 00 00]
  Send

CAN Bus: <~~~[04 74 20 10 ...]~~~~

ESP32: Parse 0x74 response -> Download request approved ✓

TIME: ~20ms (multi-frame + processing)

========================================================================================================
STEP 3: UDS 0x36 - Transfer Data (Repeat for each block)
========================================================================================================

Example: Block 1 (1024 bytes payload + 2 bytes header = 1026 total)

ESP32 (UDS layer):
  Build: [36 01 <1024 bytes firmware>]
          |  |
          |  blockSequenceCounter=1
          SID

ESP32 (CAN-TP layer):
  Length=1026 > 7 -> Multi-frame
  Build FF: [14 02 36 01 FF FF]  Length=1026 (0x0402)
            |  |              |_______|
            Type, length      First 4 bytes UDS payload
  Send FF

CAN Bus: ~~~~[14 02 36 01 ...]~~~>

STM32 (CAN-TP layer):
  Receive FF, length=1026 bytes
  Check buffer: Need 1026 bytes free? YES
  Build FC: [30 08 0A ...]  BS=8, STmin=10ms
  Send FC

CAN Bus: <~~~[30 08 0A ...]~~~~

ESP32 (CAN-TP layer):
  FC received: BS=8, STmin=10ms
  Calculate: Remaining data = 1026 - 6 (FF payload) = 1020 bytes
            CFs needed = 1020 / 7 = 146 frames
  
  Send Block 1 (CF 1-8):
    CF1: [21 ...] + delay 10ms
    CF2: [22 ...] + delay 10ms
    ...
    CF8: [28 ...] + delay 10ms
  
  Total time: 8 * 12ms = 96ms
  Wait for next FC

STM32 (CAN-TP layer):
  Receives 8 CFs, stores: 56 bytes accumulated
  More data needed? YES (1020 - 56 = 964 bytes)
  Send FC again: [30 08 0A ...]

... Repeat FC + CF blocks ~18 times total (146 CFs / 8 = 18.25 blocks)

After all CFs received:
STM32 (CAN-TP layer):
  Reassembly complete: 1026 bytes
  Extract: UDS message [36 01 <1024 data>]
  Pass to UDS layer

STM32 (UDS layer):
  Parse: SID=0x36, blockCounter=1, data=1024 bytes
  Action: Write to flash buffer at offset 0
  Build response: [76 01]
  Send via CAN-TP (SF)

ESP32: Receive 0x76 01 -> Block 1 OK ✓

TIME PER BLOCK: ~2 seconds (1.8s transfer + 0.2s processing)

REPEAT for Block 2-8:
  - Block 2: [36 02 <1024 bytes>] -> 0x76 02
  - Block 3: [36 03 <1024 bytes>] -> 0x76 03
  ...
  - Block 7: [36 07 <1024 bytes>] -> 0x76 07
  - Block 8: [36 08 <116 bytes>] -> 0x76 08 (last block, partial)

TOTAL TIME: 8 blocks * 2s = ~16 seconds

========================================================================================================
STEP 4: UDS 0x37 - Request Transfer Exit (Trigger Verification)
========================================================================================================

ESP32 (UDS layer):
  Build: [37]  No parameters

ESP32 (CAN-TP layer):
  Length=1 <= 7 -> SF
  Build: [01 37 00 00 00 00 00 00]
  Send

CAN Bus: ~~~~[01 37 ...]~~~>

STM32 (CAN-TP layer):
  Receive SF, extract: [37]
  Pass to UDS

STM32 (UDS layer):
  Parse: SID=0x37
  Action: Start verification & activation sequence
  
  PROCESSING (LONG OPERATION):
    1. Verify SHA-256 (encrypted): 21ms
       - Read 7284 bytes from buffer
       - Compute hash, compare with header
    
    2. Verify ECDSA signature: 611ms
       - micro-ecc P-256 verification
       - Public key từ embedded certificate
    
    3. AES-128-CBC decrypt: 1562ms
       - Stream-based, 256-byte chunks
       - IV from FOTA header
       - Write plaintext to Slot B flash
    
    4. Verify SHA-256 (plaintext): 21ms
       - Hash decrypted firmware
       - Compare with original_sha256
    
    5. Atomic Slot Copy B->A: ~3000ms
       - Erase Slot A pages
       - Copy 256-byte chunks with memcmp verification
       - Update BKP->DR2 checkpoints
  
  TOTAL: ~5.2 seconds

  DURING PROCESSING:
    - STM32 sends NRC 0x78 (Response Pending) before each time-consuming operation
    
    CAN Bus: <~~~[03 7F 37 78 ...]~~~~ (before ECDSA encrypted, ~611ms)
    CAN Bus: <~~~[03 7F 37 78 ...]~~~~ (before AES decrypt, ~1562ms if encrypted)
    CAN Bus: <~~~[03 7F 37 78 ...]~~~~ (before ECDSA plaintext, ~611ms)
  
  AFTER SUCCESS:
    Build response: [77]
    Send via CAN-TP

CAN Bus: <~~~[01 77 ...]~~~~ (at t=5.2s)

ESP32: Parse 0x77 -> Transfer complete, firmware activated ✓

TIME: ~5.2 seconds

========================================================================================================
PHAN 5: TIPS VA BEST PRACTICES
========================================================================================================

1. TIMING TUNING:
   - STmin: Start with 10ms, reduce to 1ms if STM32 can handle
   - Block Size: 8 frames conservative, increase to 16-32 if buffer allows
   - Timeout: Use 1000ms for FC/CF, 3000ms for UDS requests (ESP32 retries on NRC 0x78)
   - Keep-alive: Send NRC 0x78 BEFORE each time-consuming operation (>500ms)
     * Implementation: UDS_SendNegativeResponse(SID, 0x78) before ECDSA/AES
     * Client: Retry on NRC 0x78, max 10 retries (prevents timeout during ~5.2s verification)

2. ERROR RECOVERY:
   - Implement retry logic: Max 3 retries per frame
   - Log sequence numbers for debugging
   - Clear state on abort (erase partial data)

3. BUFFER MANAGEMENT:
   - Pre-allocate buffers before transfer
   - Use ring buffer for CF reassembly
   - Check free space before sending FC

4. SECURITY:
   - Always verify in Programming Session before 0x34/0x36
   - Validate address/size ranges (prevent flash overflow)
   - Implement timeout to exit Programming Session (watchdog)

5. DEBUGGING:
   - Log all CAN frames with timestamps
   - Track state machine transitions
   - Use LED indicators (ESP32: Green=Transfer, Red=Error)
